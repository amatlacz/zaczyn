# Make a chosen customization usable

Use this when setup or grow proposes or changes a rule, template, procedure, skill, library, or tool. Base it on the user's work, examples, and preferences. Reuse an existing solution before creating another; removing process is a valid improvement.

## Choose and explain

A stable working preference belongs in AGENTS (or the existing authoritative rule file). Facts and context belong in PROJECT or linked references. A repeated shape may need a template; a repeatable procedure may need a recipe or skill. Add a tool/library only for a relevant capability that is missing. A profession alone does not justify a default stack.

For each material addition, explain its purpose, where it applies, what it changes, where it lives, and how to undo it. Offer a simpler alternative when helpful. Mention cost, account access, or data movement when relevant to the choice. Use existing authorization for specified additions; obtain the unresolved choice before installing an unselected stack or changing the user's working process.

## Configure within real capabilities

Inspect available skills and tools for the selected need, and use current authoritative installation guidance when installation is needed. A name in a recommendation is not evidence of availability. Reuse the host's supported installer or settings flow; do not invent a common installation directory for all apps.

When authorized and possible, configure the selected addition in its agreed workspace or account scope. Leave sign-in and credential entry to the host's normal account flow. When the assistant cannot perform a step, provide the precise action the user can take and explain what remains blocked. A chat-only environment can draft a useful recipe or instructions without installing software.

For a custom skill, define its trigger/non-trigger, inputs, output, useful steps, checks, and non-goals. Use a suitable skill creator if available. Otherwise write a usable recipe and show an explicit way to invoke it. Native discovery requires a separate check. Keep project-specific additions separate from the shipped base.

## Verify, record, and undo

Try the chosen addition with a small relevant example and a case outside its scope. Match effort to consequence: a one-line preference needs a scope check, not a benchmark. Verify actual tool access or skill invocation when claiming it works. Distinguish a generated draft, a configured capability, and a successful trial.

Record useful selected additions in the existing setup/progress record: purpose, local path or invocation, scope, and status (proposed, selected, configured, verified, or blocked), with evidence for any verified claim. The record need not be a separate inventory file. A verified trial describes the tested case, not universal reliability. Keep availability, configuration, and successful use distinct: a skill in a list has been discovered, not tested. For session-dependent observations record when/how they were checked and recheck before relying on them. Do not label a mixed list “verified,” infer sign-in state without evidence, or call the entire skill library irrelevant from an incomplete inspection.

Keep prior content or a reversible diff before changing rules or templates. Mark superseded rules inactive. Show how to remove the selection, restore the prior version, or uninstall through the host if applicable. Undo should not erase unrelated user work. Hand the user a usable setup summary and next action rather than a catalog of speculative tools.
