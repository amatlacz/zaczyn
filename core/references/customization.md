# Make a chosen customization usable

Use this when setup or grow proposes or changes a rule, template, procedure, skill, library, or tool. Base it on the user's work, examples, and preferences. Reuse an existing solution before creating another; removing process is a valid improvement.

## Explain briefly

For each material addition, say in a sentence or two what it helps with and how to undo it. Add where it lives, its cost, account access, or data movement only when relevant to the choice. Offer a simpler alternative when helpful. Use existing authorization for specified additions; obtain the unresolved choice before installing an unselected stack or changing the user's working process.

## Configure within real capabilities

Inspect available skills and tools for the selected need, and use current authoritative installation guidance when installation is needed. Reuse the host's supported installer or settings flow; do not invent a common installation directory for all apps.

When authorized and possible, configure the selected addition in its agreed workspace or account scope. Leave sign-in and credential entry to the host's normal account flow. When the assistant cannot perform a step, provide the precise action the user can take and explain what remains blocked. A chat-only environment can draft a useful recipe or instructions without installing software.

For a custom skill, pass what is already known (when it should and should not apply, an example input and output) to the app's skill creator if one is available. Otherwise write a Markdown recipe stating when it applies and when not, inputs, output, steps, checks, and non-goals, and show an explicit way to invoke it. Keep project-specific additions separate from the shipped base.

## Verify, record, and undo

Try the chosen addition with a small relevant example and a case outside its scope. Match effort to consequence: a one-line preference needs a scope check, not a benchmark. Before marking a new skill or recipe verified, try it once in a fresh session that lacks this conversation's context.

Record useful selected additions in the existing setup/progress record: purpose, local path or invocation, scope, and status on the ladder in the workspace conventions, with evidence for any verified claim. The record need not be a separate inventory file. A verified trial describes the tested case, not universal reliability. For session-dependent observations record when/how they were checked and recheck before relying on them. Do not label a mixed list “verified,” infer sign-in state without evidence, or call the entire skill library irrelevant from an incomplete inspection.

Keep prior content or a reversible diff before changing rules or templates. Mark superseded rules inactive. Show how to remove the selection, restore the prior version, or uninstall through the host if applicable. Undo should not erase unrelated user work. Hand the user a usable setup summary and next action rather than a catalog of speculative tools.
