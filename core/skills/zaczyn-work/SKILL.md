# Work

Help the user reach the intended result with only the process that helps this task. Read the first two sections of [workspace conventions](../../references/workspace.md); read the rest before creating or changing files. If a linked file cannot be opened, say which and do not claim its guidance was applied.

## Pick the next action

| Situation | Action |
|---|---|
| Clear, small, reversible task with adequate context | Do it directly. No task note or extra setup interview. |
| Resume, a pause, or interrupted work | Use [checkpointing](references/checkpointing.md); identify the intended item and inspect its actual state. |
| Plan-only request or work with meaningful dependencies | Use [planning](references/planning.md). A plan-only request ends with the plan. |
| Existing authoritative domain workflow | Follow it; link its context and checkpoints where needed. Do not create a second plan. |
| Missing essential agreement or material | Clarify the next consequential decision; do independent work while it remains open. |

Normal follow-ups continue within the selected task without rerunning this triage. A new clearly named task should not be interrupted by a menu of unrelated open items. Follow the workspace conventions for an explicit archive request; no separate skill is needed.

When the user has selected orchestrate (the zaczyn-orchestrate skill) for this task, apply its cost-aware routing to planning, execution, and completion checking. Ordinary Work does not activate that policy.

## Establish enough intent

Use existing project/task context; setup is not a prerequisite for work, and no particular brief filename is required. Agree the useful outcome and a few concrete checks, using the user's examples, standards, and material. If the framing may be wrong, ask a natural question such as “What would make this unhelpful?” Do not ask it mechanically.

Only create a task note when work needs durable agreement, cross-session progress, or retained evidence. Use the template resolution in the workspace conventions. Include unresolved assumptions or constraints that affect the next step; label criteria as proposed when they have not been agreed. Routine criteria directly derived from an explicit request need no separate approval ceremony; ambiguous consequential choices do.

Keep sourced facts apart from assumptions and keep sources for material claims; check calculated output with a suitable tool rather than trusting its formatting. Install no default framework, and do not ask the user to pick a profession or category of work. An unavailable tool is a limitation to resolve, not a reason to fabricate output or claim a check passed.

## Carry out the work

Read the relevant selected-procedure pointers in AGENTS or the existing authority. Use those domain skills and available tools; a recipe below verified may be followed as written, but do not claim it is installed or verified. Work in useful increments; verify each significant step and update the existing progress record when one exists. Pause only at an actual unresolved decision, dependency, permission boundary, or requested gate. If new evidence changes the agreement, show the change and retain its dated reason before dependent work continues.

When the user pauses, checkpoint without closing. When the intended result is ready, check it before reporting. For a quick job, check it against the request and state briefly what was checked and anything not checked or assumed. For a task with agreed criteria or a task note, apply [review](../zaczyn-review/SKILL.md) in completion mode; it owns the checking and closure rules. Do not make the user invoke a second command for routine completion checking.

Finish with the result/path and any material limitation, or the saved next action if unfinished. Mention grow (the zaczyn-grow skill) only when the user wants an adaptation or real repetition/friction makes one useful; no mandatory lesson.
